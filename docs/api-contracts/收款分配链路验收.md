# 内部收款分配验收

所有金额和用户均为专门创建的合成夹具。使用真实 Express、认证中间件、财务服务以及应用已提交迁移构建的 0700/0600 临时 SQLite；独立只读 SQLite 回查持久化事实。无生产库、实际转账、文件上传、外部提供方调用或正式财务审批。

## 五个有界场景

1. USD 分到两张合同，部分分配保留剩余款，手工继续或既有高置信度自动匹配分完后退出收款池；自动匹配实际分配额与返回金额均为剩余余额。验证来源、客户、到账时间、币种和应收列表。历史 `INCOME` 的既有 USD 规范化输入只规范新子行，原到账不改写。普通到账/直接合同收款以及既有幂等键重放仍可用
2. 负数/零值/非数值分配、未关联或不存在的合同、已有合同关联来源、非 USD、无效来源金额及超额分配返回 400，无子记录或合同金额变化。通用创建携带来源 ID 的绕过请求同样被拒绝
3. 独立 HTTP 进程暂停在事务启动前，另一进程先分配；恢复后按当前剩余金额拒绝过时请求，保持来源与合同金额。完整分配后的重复提交拒绝且不产生新记录；历史仍保留收款池类型但余额已为零的来源也拒绝 0.005 的提交，不靠容差新增款项
4. 实际数据库认证角色允许 ADMIN/PURCHASE/SALES/FINANCE/WAREHOUSE 分配；BOSS 写入 403，停用/无认证 401。SALES/FINANCE/BOSS 可读现有收款池和合同收款轨迹；JWT 声明不能覆盖数据库角色
5. 九月合成正式合同与银行到账截止/币种/客户条件、重复分录、缺失分录构成已知差异；验证桥接结果和 ADMIN/FINANCE/BOSS 可读、SALES/PURCHASE/WAREHOUSE 被拒绝。读取不修改原始证据

## 已复现并修复

- 100 美元来源接受 `110 + (-10)`，两合同收到 110 与 -10；缺少合同 ID 还会生成未关联子行并消耗到账余额
- 60 的请求在事务开始前暂停，另一请求先分配 80；恢复后两者累计 140，超过 100 来源
- 历史币种 ` usd ` 验证通过，子记录保持非标准拼写，导致只汇总 `USD` 的合同余额漏计
- 通用创建 `sourcePaymentId` 可绕过分配，向 100 来源挂入 101。新关联子行必须改用现有分配入口；保留普通创建、已存在键的只读重放以及持久化响应中的来源字段
- 100 来源已手工分配 60，余款 40 命中唯一且金额一致的合同后，自动匹配仍传原款 100 并失败；现在实际分配额与结果均采用既有剩余余额，匹配阈值与候选规则不变
- 历史来源仍是收款池类型但已有 100 子行，可接受额外 0.005 后才标记完成。余额为零时现在先拒绝，只有实际正余额继续沿用原 0.01 比较容差

## 实现与兼容边界

`financeService.allocatePaymentToContracts` 沿用仓库现有 SQLite 写锁模式，以参数化 no-op UPDATE 先获取写锁，再在同一事务内读取来源、累计已分配额、校验目标合同并持久化全部子行。逐行值必须为有限正数；新子行存规范 `USD`，不改历史币种、不换汇。保留原有 0.01 容差和可写角色；不新增分配幂等键、反向分配或撤销接口。失败事务不消耗到账余额。

通用 `POST /finance/payments` 的新非空来源 ID 返回 400 并引导使用分配；已有幂等键命中仍直接返回原记录。TypeScript 创建请求保留该字段并注明弃用，以支持旧键只读重放；Payment 响应中的来源字段继续用于读取历史关联。
