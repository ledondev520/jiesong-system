# 银行导入链路验收

本轮仅补齐三个后端场景，没有复现需要修改生产实现的问题。所有用户、账号、交易标识、金额和文件名均为合成夹具。工作簿只在内存中生成，经回环地址发送到实际 Express/Multer/认证/服务；已提交迁移构建新的 0700/0600 临时 SQLite，以独立只读连接回查持久化事实。无真实对账单、生产上传、外部银行请求、提供方调用、转账或财务审批。

## 三个有界场景

1. ADMIN/FINANCE 的解析预览返回映射、5 个有效行与 2 个错误行；预览重复或放弃后，银行行、来源批次、发票、合同、付款及会计表完全不变。BOSS/PURCHASE/SALES/WAREHOUSE 的预览与提交返回 403，停用/未认证返回 401，即使 JWT 声明 ADMIN 也不能覆盖数据库角色。全无效或缺文件的确认返回 400，不创建空批次
2. 同一混合工作簿按当前 Controller 语义提交有效记录：4 条新增、1 条重复跳过，2 个解析错误单独在 parseErrors 返回，failed 仍为 0。独立回查收入正值/支出负值、两条连续余额、币种/账户分离、掩码账号、批次 ID/文件名/起止日期及 recordCount 与实际来源行一致。完整账号不落库，导入不生成付款或改变合同/会计余额
3. FINANCE 将美元收入关联现有销售合同、将另一支出忽略后，精确重放与更名/变更摘要、时间、交易标识的同账户/币种/余额轨迹重放均跳过，不创建空批次，保留原行 ID、原来源及 MATCHED/IGNORED 元数据。重叠来源只新增一条不同余额轨迹，原交易标识复用不能抹掉该新行。BOSS 可读取现有银行行，关联/解除/忽略写入仍返回 403；整个流程不改变合同收款或会计余额

## 既有语义与覆盖缺口

- 预览只解析；不创建可消费的预览凭证。确认重新上传并解析，当前银行导入不是月度三文件确认导入协议
- 混合有效/无效行允许提交有效部分。有效行先去重，parseErrors 与重复 errors 分开返回；本轮不改为全文件拒绝
- 既有 financeImportService 单测覆盖解析及以模拟 Prisma 验证跨币种、同批精确重复和跨来源余额轨迹去重；Controller 单测仅检查模块导出。finance-query-boundaries 集成覆盖查询，不经文件导入。新测试补齐真实 multipart/认证/数据库写入与重复提交的证据
- 本轮不声称验证 UI 的取消、浏览器请求竞争、并发导入、跨银行同后四位账户、超 50000 条历史记录、数据库故障原子性、所有文件格式、全部自动匹配/解除关联或正式金融结果

## 运行

`cd backend && umask 022 && TZ=UTC NODE_ENV=test node --test src/integration/bank-import-lifecycle.integration.js`

需要既有依赖、已生成 Prisma 客户端及 Python SQLite。测试已经加入 `npm run test:db`，保留实际全局限流，不执行 db push、共享客户端生成或依赖修改。2026-10-05 使用 CI 对齐 Node 20.19.0 通过三个子场景（TAP 含父测试共 4 个）；本轮不代替协调者的完整聚合检查。
