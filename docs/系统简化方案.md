## 一、问题诊断

### 1.1 当前系统复杂性

| 维度 | 当前状态 | 问题 |
|------|----------|------|
| 导航菜单 | **14个** | 用户选择困难，不知道从哪开始 |
| 数据库模型 | **22个** | 很多是"锦上添花"功能，增加维护成本 |
| 页面结构 | 碎片化 | 相关功能分散，需要多次跳转 |
| 功能优先级 | 混乱 | 核心功能和次要功能没有区分 |

### 1.2 当前导航结构（14个入口）

```
├── 工作台
├── 数据导入
├── 商品管理      ← 基础数据分散为4个入口
├── 供应商
├── 门店管理
├── 采购管理
├── 销售管理
├── 库存管理      ← 相关功能分散为3个入口
├── 货柜管理
├── 财务管理
├── 报表统计      ← P2功能占用一级菜单
├── 用户管理
├── 系统设置      ← 设置类功能分散
├── 操作日志
```

### 1.3 核心问题

**没有聚焦真正的业务主线**：

外贸进销存的本质就是一条线：

```
采购下单 → 货物入库 → 装柜发运(出库) → 销售结算
```

运营人员每天做的事情非常简单：
1. 录入采购合同
2. 更新库存状态
3. 创建货柜、装箱
4. 记录收付款

**但当前系统把这些简单操作分散到了14个菜单里**。

## 二、简化方案

### 2.1 新导航结构（5个入口）

```
├── 📋 工作台        ← 核心入口，快速录入+待办+概览
├── 📄 合同管理      ← 采购+销售（Tab切换）
├── 📦 库存与货柜    ← 库存+货柜（Tab切换）
├── 💰 收付款        ← 应收+应付（Tab切换）
└── ⚙️ 设置          ← 基础档案+用户+系统配置+数据导入
```

### 2.2 各模块详细设计

#### 工作台（Dashboard）

**定位**：系统的中心枢纽，打开就能开始工作

```
┌─────────────────────────────────────────────────┐
│  ★ 快速录入                                     │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐         │
│  │ + 采购  │  │ + 销售  │  │ + 货柜  │         │
│  │  合同   │  │  合同   │  │  装箱   │         │
│  └─────────┘  └─────────┘  └─────────┘         │
├─────────────────────────────────────────────────┤
│  ★ 待办事项                                     │
│  • 3笔采购待付尾款                              │
│  • 2个货柜待发运                                │
│  • 5件商品待入库                                │
├─────────────────────────────────────────────────┤
│  ★ 数据概览                                     │
│  库存商品: 156件   本月采购: ¥12.3万            │
│  待发货柜: 2个     应收账款: $8,500             │
└─────────────────────────────────────────────────┘
```

**功能要点**：
- 一键进入"新建采购"、"新建销售"、"新建货柜"
- 待办事项直接显示，点击可跳转处理
- AI助手浮窗始终可用

#### 合同管理

**结构**：Tab切换，不需要跳转页面

```
┌─────────────────────────────────────────────────┐
│  [采购合同]  [销售合同]                          │
├─────────────────────────────────────────────────┤
│  🔍 搜索: ________  状态: [全部▼]  供应商: [全部▼]│
├─────────────────────────────────────────────────┤
│  合同号      供应商      金额      付款状态      │
│  CG2500123   佛山瓷砖    ¥8,500   已付定金      │
│  CG2500122   广州卫浴    ¥12,000  待付款        │
│  ...                                            │
└─────────────────────────────────────────────────┘
```

**功能要点**：
- 采购/销售在同一页面，Tab切换
- 列表直接显示关键状态（付款、库存）
- 点击合同号展开详情（弹窗或侧边栏），不跳转页面

#### 库存与货柜

**结构**：Tab切换

```
┌─────────────────────────────────────────────────┐
│  [库存状态]  [货柜管理]                          │
├─────────────────────────────────────────────────┤
│  Tab1: 库存状态                                 │
│  ┌──────────────────────────────────────────┐  │
│  │ 商品      采购合同    状态      操作     │  │
│  │ 800瓷砖   CG2500123   生产中    [入库]   │  │
│  │ 马桶      CG2500122   已入库    [出库]   │  │
│  └──────────────────────────────────────────┘  │
├─────────────────────────────────────────────────┤

│  ┌──────────────────────────────────────────┐  │
│  │ 货柜号    港口   箱数   状态    操作      │  │
```

**功能要点**：
- 库存和货柜密切相关，放在一起
- 库存按采购合同/商品组织，显示当前状态
- 货柜支持快速装箱操作

#### 收付款

**结构**：Tab切换

```
┌─────────────────────────────────────────────────┐
│  [应付账款]  [应收账款]                          │
├─────────────────────────────────────────────────┤
│  供应商/门店    合同      应付/收    已付/收     │
│  佛山瓷砖       CG2500123  ¥8,500    ¥2,550    │
│  禧瑞都门店     EXP2500001 $3,200    $3,200 ✓  │
└─────────────────────────────────────────────────┘
```

**功能要点**：
- 应付（给供应商）和应收（从门店）在同一页面
- 直接显示欠款金额，一目了然
- 点击可快速记录付款

#### 设置

**结构**：二级分组

```
┌─────────────────────────────────────────────────┐
│  ★ 基础档案                                     │
│  [商品管理]  [供应商管理]  [门店管理]            │
├─────────────────────────────────────────────────┤
│  ★ 系统管理                                     │
│  [用户管理]  [系统配置]  [数据导入]              │
└─────────────────────────────────────────────────┘
```

**功能要点**：
- 不常用的功能收纳到设置里
- 基础档案（商品/供应商/门店）合并为一个入口
- 数据导入、用户管理都在这里

## 三、数据模型简化

### 3.1 模型精简对比

| 类别 | 当前模型 | 简化后 | 说明 |
|------|----------|--------|------|
| **核心业务** | | | |
| 用户 | User | User | 保留 |
| 供应商 | Supplier + SupplierAlias | Supplier | 合并别名为字段 |
| 门店 | Store + Port | Store | 港口改为枚举字段 |
| 商品 | Product + ProductCategory + ProductSupplier | Product + ProductSupplier | 去掉分类，简化为tags |
| 采购 | PurchaseContract + PurchaseItem | 保留 | 核心模型 |
| 销售 | SalesContract + SalesItem | 保留 | 核心模型 |
| 货柜 | Container + ContainerItem | 保留 | 核心模型 |
| 付款 | Payment | 保留 | 核心模型 |
| **辅助功能** | | | |
| 库存 | Inventory | **删除** | 合并到PurchaseItem.status |
| 价格历史 | PriceHistory | **延迟** | V2再实现 |
| AI聊天 | ChatHistory + TokenUsage | **延迟** | V2再实现 |
| 操作日志 | OperationLog | **延迟** | V2再实现 |
| 通知 | Notification | **延迟** | V2再实现 |
| **配置** | | | |
| 系统配置 | SystemConfig | 保留 | 含港口枚举 |
| 导入记录 | ImportRecord | 保留 | 数据导入必须 |
| 合同文件 | ContractFile | 保留 | 文件管理必须 |

### 3.2 简化后模型数量

| 维度 | 当前 | 简化后 | 减少 |
|------|------|--------|------|
| 数据模型 | 22个 | **12个** | -45% |

### 3.3 库存模型简化说明

**当前设计**：独立的 `Inventory` 模型

```
PurchaseItem (采购明细)
     ↓
Inventory (库存记录)  ← 独立实体
     ↓
Container (货柜)
```

**简化设计**：库存状态作为采购明细的字段

```prisma
model PurchaseItem {
  id                 String   @id
  // ... 其他字段
  
  // 库存状态字段（替代独立的Inventory模型）
  inventoryStatus    String   @default("PRODUCING")  // PRODUCING/PACKING/SHIPPING/INBOUND/OUTBOUND
  inboundAt          DateTime?                       // 入库时间
  outboundAt         DateTime?                       // 出库时间
  containerId        String?                         // 关联货柜
  salesContractId    String?                         // 出库时关联的销售合同
}
```

**好处**：
- 减少一个实体，简化查询
- 采购→库存→出库 的流转更直观
- 不需要维护采购明细和库存的一对一关系

## 五、实施路径

### Phase 1: 导航重构

1. 修改 `Sidebar.tsx`，从14个菜单精简到5个
2. 创建Tab组件，用于页面内切换
3. 调整路由结构

### Phase 2: 页面整合

1. 重新设计工作台页面
2. 合并采购/销售到"合同管理"页面
3. 合并库存/货柜到"库存与货柜"页面
4. 合并应收/应付到"收付款"页面
5. 整合设置页面

### Phase 3: 数据模型简化

1. 删除 `Inventory` 模型，字段合并到 `PurchaseItem`
2. 删除 `Port` 模型，改为 `SystemConfig` 枚举
3. 删除 `SupplierAlias`，合并到 `Supplier.aliases` 字段
4. 删除 `ProductCategory`，简化为 `Product.tags`
5. 暂时移除未使用的模型（ChatHistory, OperationLog等）

### Phase 4: API精简

1. 移除不需要的API端点
2. 简化API响应结构
3. 统一错误处理
