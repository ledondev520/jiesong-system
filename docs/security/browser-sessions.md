# Optional fixed-expiry browser login

## Protocol and threat boundaries

- `rememberMe` is an optional strict boolean on `POST /auth/login`; the UI defaults off and warns about shared devices. Unchecked login keeps the existing JWT/sessionStorage behavior for tabs and machine clients. No password is saved by app code; browser password-manager autocomplete remains enabled.
- After the existing password verification succeeds, the checked path creates a random 256-bit opaque credential. `browserSessionService.js` persists only its SHA-256 digest, user ID, sessionVersion, creation time and absolute expiry. The expiry is copied from the already-issued, verified JWT and the existing `JWT_EXPIRES_IN`; there is no refresh, rolling expiry or longer lifetime. The JWT used to derive expiry is never returned in this path. The response contains `token: null`, public user data, expiry and a CSRF proof.
- Production cookie: `__Host-jiesong_session; HttpOnly; Secure; SameSite=Strict; Path=/; Expires=<original expiry>`, without Domain. Secure is unconditional in production, never based on forwarded headers. Local/test HTTP uses `jiesong_session`. Deployment requires HTTPS and an exact frontend origin in `CORS_ORIGIN`; cookie auth does not support cross-site frontend/API deployments. Same-origin `/api/v1` proxying is preferred. No new runtime secret/config variable is introduced.
- `GET /auth/session` reads the current account, active status, role, sessionVersion and session expiry from SQLite, returns a session-bound HMAC CSRF proof, and never refreshes or writes a cookie. All auth responses are `private, no-store`. No persistent credential is returned to JavaScript. The proof is only kept in memory; it is not sufficient to authenticate without the HttpOnly cookie.
- Cookie-authenticated POST/PUT/PATCH/DELETE and other unsafe methods require both exact allowlisted Origin and `X-CSRF-Token` bound to that cookie, compared at fixed length in constant time. Missing/null/untrusted origins fail closed. Fetch-Metadata cross-site requests are rejected; same-site reads from sibling origins require explicit trusted Origin too, including GET endpoints that may trigger upstream work. Host and forwarding headers cannot authorize a production origin. Only nonproduction with no explicit allowlist permits localhost origins.
- Persistent/cookie-overwriting login requires a trusted origin before password verification. This prevents login CSRF. Explicit nonempty Authorization takes precedence; malformed/expired bearer never falls back to a different cookie identity. Empty legacy Authorization headers allow cookie auth. Existing JWT and Agent authorization behavior otherwise stays intact.
- `GET /auth/logout-csrf` is a no-store, logout-only proof read requiring Fetch-Metadata same-origin or an exact trusted Origin. It returns only the current cookie-bound CSRF (null for absent/malformed cookie), never a profile or credential, and works even after expiry/disable/version revocation. The client reads it without an automatic bearer and never stores it in authenticated state, so legacy-bearer tabs can explicitly revoke the current shared-browser cookie without trusting that bearer or stale CSRF. Cookie replacement between proof and logout fails safely.
- `POST /auth/logout` requires the cookie's own Origin/CSRF even if an Authorization header is supplied and deletes only that cookie's database row, without global sessionVersion increments or other-browser logout. Password changes/resets and administrator password writes retain the existing sessionVersion invalidation; every cookie request checks the live version and active status.
- Revocation/401/password-change responses intentionally do not send cookie deletion headers. A delayed old response must not erase a newer login at the browser network layer. A revoked opaque cookie may remain until its original expiry or the next successful login, but it cannot authenticate. Successful unchecked login explicitly revokes the current cookie and expires it; checked login atomically replaces only this browser's row. Failed login preserves the existing session. Malformed/duplicate cookies fail authentication but do not prevent a trusted correct new login.
- Expired database rows are lazily deleted during the next successful checked login. Logout immediately deletes its row; deleted users cascade their sessions. Version-revoked records carry no usable credential and remain until their original expiry is pruned. No background renewal or retention-extending write occurs. Database errors are sanitized before generic error logging and return 503 without credentials/digests.

## Frontend safety

`login/page.tsx` probes the live session, serializes submits and aborts/ignores late login completion after navigation. `dashboard/layout.tsx` withholds protected children and old-role navigation until cookie restoration succeeds; transient failures show retry instead of falsely reporting expiry. Header and mobile logout wait for server revocation, retain state on network failure and guard late completion against a new auth generation. A single in-flight logout prevents duplicate clear/revocation requests.

`browser-session.ts` holds only the CSRF proof and an auth generation. Login/logout/expiry clear the Axios, business-data and idempotent-result caches. Generations prevent old requests refilling cleared caches, old 401s logging out a new user, and old delayed expiry prompts/actions redirecting a newer login. Idempotency HTTP keys are unchanged. Axios includes credentials and CSRF; multipart contract uploads, tax-refund POST exports and AI POST streams also send the proof. Same-origin GET/download fetches use browser default credentials.

## Migration and rollout

`20261005070032_browser_sessions` only adds a table, two indexes and a user cascade relationship. It does not rebuild user/business tables, update passwords/versions, change JWT secrets or revoke existing bearer sessions. Development generation used `npm run db:migrate` after a protected backup of an isolated synthetic database. Never use `db push`.

Before production migration, the release coordinator must verify a fresh, consistent SQLite online backup of the actual resolved `DATABASE_URL` through the reviewed release preflight. Resolve environment precedence and relative SQLite paths correctly; include committed WAL contents, use a unique destination (0700 directory/0600 file), check integrity, retain old backups and do not print private paths or credentials. The general development backup script's default path/copy behavior is not sufficient proof of a production snapshot. This PR does not modify deployment workflows or perform a production migration. Existing CI/deploy migration execution remains unchanged; fresh backup verification is a mandatory separate release gate.

Deploy backend migration/generated Prisma client before enabling the new frontend. Verify HTTPS cookie flags, exact CORS/CSRF allowance, same-origin proxy propagation and a synthetic authorized production acceptance flow. On rollback, prefer previous application code while retaining the additive unused table and subsequent business writes. Revoke new browser sessions before a later re-enable if required; never blindly restore an old database over newer business records. Previous code does not authenticate this cookie and existing bearer clients remain compatible.

Covers existing-expiry equality/no renewal, production flags, origin/CSRF failures, multipart/SSE gates, bearer precedence, BOSS bootstrap/logout, two-browser independence, bad/unchecked login, expiry/disabled/version/password invalidation, and sanitized persistence failure.

- `cd frontend && npx playwright test e2e/browser-session.spec.ts --workers=1 --reporter=list`: real production Next build/rewrite plus a synthetic Express/SQLite backend on local port 3001. Actual persisted Chromium profile shutdown/reopen, reload/new tab, default tab-only login, failed login, CSRF rejection, expiry, logout and cookie replay. No auth response mocks or production data. The test backend does not run application startup jobs and is guarded by test mode, a protected temporary directory, an IPC parent and random environment-provided credentials. Run with the default local API base and no service already bound to port 3001.

## Recognized global HTTP admission control

`middleware/apiRateLimit.js` replaces the custom global limiter with the already locked express-rate-limit, preserving 100/min, placement before parsing/routers, legacy 429 JSON, Retry-After seconds and X-RateLimit-Reset milliseconds. `ipKeyGenerator(req.ip)` canonicalizes mapped IPv4 and IPv6/56 without reading untrusted forwarding headers or enabling proxy trust. The existing tighter login 10/15min and recovery limits remain. Standalone auth HTTP fixtures mount the same limiter, and tests cover 100 allowed/101st rejected, no parsing before denial, canonical buckets, untrusted-header spoofing and explicit trusted proxies. No CodeQL rule or finding is suppressed.

These HTTP counters remain process-local, matching the replaced implementation: restarts reset them and workers have independent budgets. This is not a new distributed or durable quota; existing persistent SQLite email/recovery quotas still apply independently.
