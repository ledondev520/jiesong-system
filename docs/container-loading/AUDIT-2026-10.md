- Hapag-Lloyd fleet page (reference, blocked for automated fetch): https://www.hapag-lloyd.com/en/services-information/cargo-fleet/container/40-standard-high-cube.html.

Current code uses 12030 × 2350 × **2690** (frontend + readiness) and 12032 × 2352 × 2698 (containerService). Neither knows the door size; oversize cartons that pass the inner dimensions but not the door are not detected (P2).

**Weight limits in practice.** The ISO payload (26–28 t) is not the binding limit: road limits at both ends are. The owner's 22 t matches common practice for 40' on Chinese roads; on the US side a 40' at 22 t cargo usually exceeds the standard-chassis cargo limit and needs a tri-axle chassis or overweight handling. Seapot buys FOB, so US drayage is the buyer's cost, but it is worth a line to the customer (owner question Q5).

## 4. Audit

### 4.1 Algorithm and fill-rate quality

The packer (`binPacking.ts:207-344`, duplicated in `shipmentReadinessService.js:73-151`):
1. Expands every line to single cartons, sorts by carton volume descending.
2. Keeps a list of free spaces; for each carton takes the first space ordered by (z, y, x) where it fits in one of two yaw orientations.
3. Splits the used space into right / front / top remainders with a 10 mm gap and drops remainders ≤ 100 mm.

It is a reasonable first-fit guillotine heuristic for uniform cartons, but: volume ordering puts small heavy cartons last; the guillotine split of a tall floor space strands vertical space above short cartons once neighbouring spaces are consumed; there is no weight, support, stack or door awareness.

Measured by running the existing backend copy unchanged on reference cases (Node 22, this VPS; script kept out of the repo):

| Case | Cartons (total CBM) | Current packer | Notes |
|---|---|---|---|
| A tiles-only: 700 × 620×620×50 mm, 31 kg | 700 (13.5) | 700 placed, 21.7 t, 13 layers, bottom carton carries 372 kg, 13 ms | Weight-bound load (99% of 22 t, 20% of 68 CBM). Floor-first fills the whole floor, so weight is spread. But 800 cartons (24.8 t) are **all** placed: no payload cap. |
| B2 chairs-only: 200 × 650×600×950 mm, 14 kg | 200 (74.1) | **108** placed | Geometric maximum is 120 (600 mm side along the length, 20 × 3 × 2). The 10 mm gap and fixed orientation order lose 10%. |
| B furniture-only: 12 sofas 2100×950×850, 60 chairs, 20 tables 1600×900×180, 50 stools 450×450×480 | 142 (52.6) | **95** placed (37.4 CBM), 47 unplaced | 77% of the 68 CBM limit — should fit or come close. |
| C mixed: 300 tile cartons + 12 sofas + 80 chairs + 60 stools | 452 (61.6) | **100** placed, **all 300 tiles unplaced**, 352 unplaced | Gate reports 「仍有 352 箱无法装入 40HQ 货柜」 for a load at 81% of inner volume. |
| Perf: 600 mixed small cartons | 600 (40.9) | all placed, 5 ms | Speed is not the problem. |

A scratch block-building prototype of the §5.3 design (also not committed) on the same cases: A 700 placed in 1 ms and 800 → 709 placed at 21 979 kg (payload cap); B2 **120**; B 130/142 placed (48.2 CBM) with stack limits; C **396/452**, all 300 tiles on the floor, nothing heavy on furniture; 600 cartons 0.3 ms; 30 SKUs × 12 cartons 26 ms. These numbers set the test bounds in §5.8.

### 4.2 Weight and volume limits

- Utilisation uses contract header totals (`SalesContract.grossWeight/volume`), which are normally the sum of lines (`salesService.js:458-480`) but can be set directly on create/update (`salesService.js:361, 419`). The packer uses line data. Two sources for one number (P2).
- The packer has no payload cap (A with 800 cartons places 24.8 t). Overweight is only caught by the header total check (P0 together with F2: the 3D plan shows an impossible load as fully placed).
- Utilisation bars cap at 100% (`SalesDetailPageContent.tsx:821, 828`), hiding the size of an overload; the text still says 超过 (P3).

### 4.3 The 80% check today vs PRD:138

PRD:138: 40HQ safe limits 22 t / 68 CBM; when **any** utilisation reaches 80% **and** all cartons fit, 确认发运 is allowed; over limit or unplaced cartons block.

| Rule | Frontend `evaluateShippingReadiness` | Backend `evaluateShipmentReadiness` | PRD |
|---|---|---|---|
| weight ≥ 80% OR volume ≥ 80% | yes | yes | yes |
| over 22 t / 68 CBM blocks | yes | yes | yes |
| unplaced cartons block | yes | yes | yes |
| no packing lines blocks | no (vacuously "fits") | yes | implied |
| line without carton count blocks | **no** | yes | implied |
| compare on unrounded values | no (rounded to 0.1 first) | no (`toFixed(1)`) | — |
| estimated dims labelled 「估算」 | partly (「已预估」 in 3D tooltip; detail page counts lines) | counted, not reported in message | must label |
| list page badge | header totals only, no physical fit | — | — |

So the logic matches PRD:138 in the backend, the UI copy has drifted (F4), and the rounding edge (F10) applies to both.

### 4.4 Stacking, orientation, fragile, max stack load

None implemented. Orientation is yaw-only (length/width swap), which is accidentally safe for "this side up" but forbids laying cartons on their side when that is allowed and would fit. There is no support check beyond "space above a placed carton" (top spaces are created with the carton footprint, so 100% support — fine), no per-carton or per-product stack-load limit, no fragile/no-stack flag, and no heavy-at-bottom ordering. Nothing in the schema stores handling flags (`Product` has `categoryId` only).

### 4.5 Multi-container splitting

None. `SalesContract` is the container (one contract = one physical box, `containerLabel`). The gate blocks when cartons do not fit, but the UI cannot answer "how many 40HQ would this need" or "which cartons are left over".

### 4.6 Usability (desktop and mobile)

- Desktop: 3D view is useful but has no legend (colour → product), no list of unplaced cartons, no load sequence, no print/export, and only 40HQ. Every hover re-renders every carton and allocates a new edges geometry (`Container3DView.tsx:93-96`), so 700 tiles stutter.
- Mobile: three.js is loaded on phones; help text mentions mouse wheel and right-click; tooltips need hover. Redesign §8 says no 3D on mobile.
- Messages hard-code 22t / 68 CBM / 40HQ in four places (`SalesDetailPageContent.tsx:845, 990, 1027, 1073, 1140, 1535`; `salesService.js:280-286`; `tradeWorkflowService.js:226, 307`; `sales/page.tsx:576`).

## 5. Design

### 5.1 Decision: the backend owns specs, packing and the check; the frontend renders a plan

**One implementation, in the backend, exposed as a read-only API.** The frontend stops packing.

Why:
- The backend gate in `salesService.js:276` is authoritative and must stay there. Any frontend copy is a second implementation that drifts (F3/F4 are exactly that).
- The frontend cannot import repo-root modules in production: `frontend/next.config.ts:129-131` pins `turbopack.root` to `frontend/`, and Vercel/Render build from `cd frontend`. Moving the root is a build-config change with deploy risk, out of scope here. (Frontend **tests** may import `config/*.json`, as `PricingConfigCard.test.tsx:5` already does.)
- A plan request is one GET on a page that already fetches the contract; packing a few hundred cartons costs single-digit milliseconds (§4.1).
- The redesign wants a self-contained 货柜 component (`<ContainerLoadingPanel salesContractId=… />`) — fetching its own plan fits that.

Rejected: shared TS package (build root change), generated frontend copy + sync test (still two runtimes to test), frontend-only packer (cannot be the gate).

**Consequence for the cards:** C3's tests are backend `node --test` (`backend/src/services/*.test.js`), not frontend vitest. Frontend vitest covers rendering (C3 3D adapter, C4).

### 5.3 Packing algorithm (C3): block-building extreme-point heuristic

File `backend/src/services/containerPacking.js`. Pure, synchronous, no I/O, deterministic.

**Input normalisation** `toCartonLines(packingItems, config)` (replaces both `buildPackingBoxes` and `buildBoxes`):
- One entry per packing line with `boxes > 0`: `{ lineId, productId, name, count, kgPerCarton = line.grossWeight / boxes (F8 fix), dims, dimsSource, profile, color }`.
- Dimension source order: line L/W/H → **estimate** from `line.volume / boxes` → (only if product dims and the line has `quantity == boxes`, i.e. one piece per carton) product L/W/H → none. `dimsSource ∈ 'line' | 'product' | 'estimated' | 'missing'`. The product fallback is restricted because product fields are per 件 (schema 256-263; owner Q6).
- Estimation keeps the current 1.2 : 1 : 0.8 ratio (clamped to the usable inner box). **No volume → `missing`** (blocker), never the 500×400×300 fabrication (F6).
- Dimensions rounded to integer mm; colour from `productId` with a larger deterministic palette.

**Ordering** (stable): heavy lines first (by density desc), then base area desc, height desc, `lineId` asc.

**Main loop** (one container at a time):
1. Extreme points (EPs) start at `(0,0,0)`; x runs from the rear wall (0) to the door (`usable.length`), y across, z up.
2. Take the highest-priority line with cartons left whose carton still fits the remaining payload. For each EP in order (x, z, y ascending) and each allowed orientation (`upright`: 2 yaw orientations; otherwise all 6; heavy/tile: largest face down), build the largest **block** `nx × ny × nz` of that carton at the EP:
   - `nz` ≤ stack cap `floor(maxStackKg / kgPerCarton) + 1` and fits height; **heavy lines spread over the floor**: `nz = min(cap, ceil(count / (nxMax × ny)))` so the block spans the length and the centre of gravity stays near the middle;
   - then `ny`, then `nx = min(fit, ceil(remaining / (ny × nz)))`; shrink each until the block overlaps no placed block;
   - the last partial block is split into full columns plus one partial column (two blocks).
3. Accept the first EP/orientation where the block is valid, preferring the larger block on ties. Valid means:
   - inside the usable box, no overlap (AABB against placed blocks);
   - z = 0, or ≥ `minSupportRatio` of the base rests on block tops at exactly z;
   - heavy cartons only on the floor or on heavy blocks;
   - for every supporting block, transitively down to the floor: `(nz−1)·kg + load from above ≤ maxStackKg` of that block's carton (load from above = new block weight × overlap area / base area, applied per carton footprint);
   - cumulative weight ≤ `min(safeGrossKg, maxPayloadKg)`.
4. Place, update EPs (remove covered, add the three corner projections), repeat. When no line can be placed, start a gap-filling pass with single-carton blocks for remaining lines (same rules, at most 2 000 attempts), then close the container.
5. If cartons remain and at least one carton was placed, open the next container of the same type (overflow) and repeat. Cartons that fit no empty container (larger than usable inner box in every allowed orientation, or cannot pass the door: for some allowed orientation `width ≤ door.width && height ≤ door.height`) go to `unplaced` with a reason.

Complexity: O(blocks × EPs × orientations × blocks). Blocks stay in the tens for typical orders (prototype: 2–54 blocks). Budget: **≤ 50 ms for 600 cartons / 30 SKUs in Node 22**, because `tradeWorkflowService` may pack every contract (§4.7). Test guard < 200 ms in CI.

Determinism: no randomness, no `Date`, stable sort with `lineId` tie-break, integer arithmetic on mm, iteration over arrays only.

### 5.4 Result shape (shared by 3D, 2D/mobile, print)

Backend JSDoc in `containerPacking.js`; frontend mirrors it as TypeScript types in `frontend/src/lib/containerLoading.ts` (types + formatting only). Coordinates in mm, origin = rear-left-floor, x toward the door.

```ts
type ContainerTypeCode = '20GP' | '40GP' | '40HQ';

interface ContainerSpecView {
  code: ContainerTypeCode; label: string;
  innerMm: { length: number; width: number; height: number };
  usableMm: { length: number; width: number; height: number };
  doorMm: { width: number; height: number };
  safeGrossKg: number; safeVolumeCbm: number; maxPayloadKg: number;
}

interface PlanLine {                      // one per packing line
  lineId: string; productId: string; name: string; color: string;
  cartons: number; kgPerCarton: number;
  cartonMm: { length: number; width: number; height: number } | null;
  dimsSource: 'line' | 'product' | 'estimated' | 'missing';   // 'estimated' => UI label 「估算」
  profile: 'tile' | 'furniture' | 'default'; heavy: boolean; upright: boolean; maxStackKg: number;
}

interface PlacedBlock {                   // in load order = loading sequence (装货顺序)
  step: number; lineId: string;
  x: number; y: number; z: number;        // block min corner
  nx: number; ny: number; nz: number;     // cartons along x / y / z
  cartonMm: { length: number; width: number; height: number };   // oriented
  cartons: number; kg: number;
}

interface LoadedContainer {
  index: number;                          // 0 = this contract's container, 1.. = overflow
  blocks: PlacedBlock[];
  cartons: number; grossKg: number; cargoCbm: number;
  weightPct: number; volumePct: number;   // vs safe limits, unrounded
  usedHeightMm: number; cogXmm: number;   // centre of gravity along the length
}

interface UnplacedLine { lineId: string; cartons: number; reason: 'oversize' | 'door' | 'missing-dimensions' | 'no-space' }

interface LoadingPlan {
  algorithm: 'block-ep-v1';
  containerType: ContainerTypeCode; container: ContainerSpecView;
  availableTypes: Array<{ code: ContainerTypeCode; label: string }>;
  lines: PlanLine[];
  containers: LoadedContainer[];
  unplaced: UnplacedLine[];
  totals: { cartons: number; grossKg: number; cargoCbm: number };   // from packing lines
  check: LoadingCheck;                    // §5.5
}
```

Consumers:
- **3D** (`Container3DView`, C3 adapts minimally): props `{ plan: LoadingPlan; containerIndex?: number }`; one `InstancedMesh` per block (fixes the per-carton geometry churn), frame from `plan.container.innerMm`, estimated lines with the existing amber edge.
- **2D top + side SVG** (C4, `ContainerPlan2D.tsx`): blocks projected on x/y (top) and x/z (side), colours from `lines`, door marked on the right. Used for mobile and print.
- **Print** (C4): per container a page with header (contract no., type, cartons, kg, CBM, %), top + side SVG, legend table (line, name, cartons, kg, carton size, 「估算」 badge), and the loading-sequence table from `blocks` (step, product, nx×ny×nz, cartons, kg, distance from rear wall).

```ts
interface LoadingCheck {
  ready: boolean;
  status: 'ready' | 'under-utilised' | 'blocked';
  weightPct: number; volumePct: number; thresholdPct: number;
  reachedBy: 'weight' | 'volume' | 'both' | 'none';
  blockers: Array<{ code: BlockerCode; message: string }>;   // non-empty => status 'blocked' (or 'under-utilised' if that is the only one)
  warnings: Array<{ code: WarningCode; message: string }>;
  headline: string;                                          // first blocker message, else ready/warning text
}
```

Rules (PRD:138): compare **unrounded** percentages with `≥ thresholdPct` (79.95% fails); ready = no blockers. Totals come from packing lines (same as `recalculateContractStats`), not the editable header.

Messages (Chinese UI text; `{}` filled by the function, numbers formatted to 1 decimal):

| Code | Kind | Message |
|---|---|---|
| — | ready headline | `可出柜：体积 {v}%、毛重 {w}%，全部 {n} 箱已装入 1 个{type}` |
| `missing-packing-items` | blocker | `尚未录入装箱明细` |
| `missing-box-count` | blocker | `{k} 行装箱明细未填写箱数` |
| `missing-dimensions` | blocker | `{name} 缺少箱规和体积，无法排柜，请补充箱规（长×宽×高）` |
| `over-weight` | blocker | `超重：毛重 {kg} kg，超过{type}安全上限 {limit} kg` |
| `over-volume` | blocker | `超体积：{cbm} CBM，超过{type}安全上限 {limit} CBM` |
| `oversize` | blocker | `{name} 箱规 {l}×{w}×{h} mm 超过{type}内尺寸，无法装入` |
| `unplaced` | blocker | `仍有 {n} 箱装不下，共需 {m} 个{type}，请拆分订单或更换柜型` |
| `under-utilised` | blocker | `未达出柜标准：体积 {v}%、毛重 {w}%，任一需达到 {t}%` |

Status: `blocked` if any blocker other than `under-utilised`, else `under-utilised` if that one is present, else `ready`. Estimated dimensions do not block on their own (PRD:139) but the `estimated` warning is always shown next to the result.
