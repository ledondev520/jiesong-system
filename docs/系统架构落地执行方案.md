# 系统架构落地执行方案（V1）

> 若本文件夹结构或内容变化，请更新 `docs/README.md` 与根 `README.md` 的文档导航。

## 目的/边界/职责
- 目的：给出从“架构设计”到“前后端落地+验收发布”的可执行路线图。
- 边界：聚焦当前仓库（frontend/backend/docs/CI），不涉及外部系统改造。
- 职责：作为多 Agent 协同执行的总纲与验收基线。

## 1. 目标与完成定义（DoD）

### 1.1 总目标
- 在不破坏现有业务流程的前提下，建立“可并行、可验证、可回滚”的系统演进机制。
- 让架构师可调度前端、后端、契约、数据库、质量五类角色形成闭环交付。

### 1.2 全局 DoD
- 每个工作单元（WU）有明确输入/产出/验收脚本/回滚点。
- 每轮结束至少通过：后端单测、前端单测、前端 E2E 冒烟。
- 文档与代码同步：目录变化、职责变化、接口变化必须更新对应 README/台账。

## 2. 角色矩阵与协同协议

| 角色 | 主职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| `system-architect-orchestrator` | 全局建模、任务编排、里程碑治理 | 需求/现状/风险 | 分阶段执行清单、跨角色调度单 |
| `frontend-polish-orchestrator` | 前端阶段拆解与推进 | 架构目标、页面范围 | 前端阶段任务包、页面覆盖清单 |
| `frontend-polish-engineer` | 前端页面与组件落地 | 前端任务包 | 页面改造代码、测试补齐 |
| `dashboard-visual-director` | dashboard 专项设计与体验升级 | 前端任务包 | 工作台信息架构与视觉实现 |
| `backend-system-engineer` | 服务/API/模型落地 | 架构目标、契约约束 | 后端实现与测试 |
| `api-contract-coordinator` | 接口契约、兼容与联调节奏 | 前后端方案 | 契约文档、联调状态面板 |
| `database-migration-architect` | Schema 迁移与数据回滚策略 | 数据变更需求 | 迁移脚本策略、核验与回滚方案 |
| `quality-verification-guardian` | 质量门禁与发布建议 | 改动清单、测试结果 | 验收报告、发布结论 |

## 3. 分阶段落地（可并行）

### Phase F：架构执行基线（本轮）
- F-1：梳理现状与目标态差距（架构师）
- F-2：固化 WU 模板（输入/输出/脚本/回滚）（架构师 + 质量）
- F-3：选择一个高价值业务链路做端到端实战（前后端 + 契约 + 质量）

### Phase G：高价值链路实战
- G-1：选定链路（建议：采购->库存->财务收口）
- G-2：前后端并行改造与联调
- G-3：回归验收与发布建议

### Phase H：规模化复制
- H-1：把实战模板复制到其余业务链路
- H-2：建立周节奏指标看板（质量/效率/回归率）

## 4. 本周执行清单（Start Now）

| WU ID | 内容 | Owner Agent | 验收脚本 | 回滚点 |
|---|---|---|---|---|
| WU-F-01 | 输出业务链路优先级与里程碑 | `system-architect-orchestrator` | 文档评审通过 | 回退到上版方案文档 |
| WU-F-02 | 定义采购链路 API 契约与联调面板 | `api-contract-coordinator` | 契约示例可被前后端复现 | 回退到旧契约版本 |
| WU-F-03 | 后端采购链路关键接口稳定性加固 | `backend-system-engineer` | `cd backend && npm run test` | 回滚本轮后端改动 |
| WU-F-04 | 前端采购链路交互一致性与错误态补齐 | `frontend-polish-engineer` | `cd frontend && npm run test` | 回滚本轮前端改动 |
| WU-F-05 | 端到端冒烟与发布结论 | `quality-verification-guardian` | `cd frontend && npm run test:e2e` | 按失败项回滚对应 WU |

## 5. 质量门禁
- 必跑：`cd backend && npm run test`
- 必跑：`cd frontend && npm run test`
- 必跑：`cd frontend && npm run test:e2e`
- 可选：`cd frontend && npm run test:coverage`

## 6. 风险与回滚策略
- 风险：接口变更导致前后端错配  
  - 预案：所有字段变更先过 `api-contract-coordinator`。
- 风险：数据结构变更引发兼容问题  
  - 预案：涉及 schema 变更必须先过 `database-migration-architect`。
- 风险：改动扩散导致回归成本上升  
  - 预案：小步提交 + WU 级别回滚 + 质量守门后再进入下一 WU。
